# 内容审计：白名单照审照拦 + Server酱微信推送 + Jev 降本

## 背景

- us-40 的内容审计引擎是 TypeSafe Jev（`jev-latest`，13 个 noul 问题，pre_block 同步拦截）。2026-10-05 启用，2026-11-08 14:24 余额耗尽（HTTP 402）。之后审计失败一律放行，日志只显示 `no moderation api key available`，静默放行了 4 天多，2026-11-12 约 22:00 起审计被关闭。
- 11-11 03:00 到 11-12 22:00 这 43 小时有完整的审计记录，共 178,213 次调用：
  - 84.6% 来自风控白名单用户 16、2、22。他们只记录、永不拦截，并且审计是同步执行的。
  - 57.2% 落在之后被 sub2api 本地拒绝的请求上，例如无可用账号 503、并发 429、RPM 429、余额不足 403。原因是审计在这些检查之前执行，客户端每重试一次就再审一次。
  - 历史命中的 7,153 次里只有 1,244 条不同内容，因为违规哈希预检没有打开。
  - 短文本里有 49% 是完全重复的，例如 `hi`、`ping`、`.` 这类探活请求。
- sub2api 不记录 Jev 的 token 用量（`content_moderation_typesafe.go` 把 usage 丢掉了），唯一的出站通知是邮件。生产上 ops 告警的收件人为 0，告警等于发不出去。

## 已确认的决策（2026-11-14 grilling）

| # | 主题 | 决定 |
|---|---|---|
| D1 | 白名单在审计上 | 和普通用户完全一样：同样的阈值，会拦截、发违规邮件、计入封号次数 |
| D2 | 白名单拆分 | `cyber_policy_user_allowlist` 只管 OpenAI cyber_policy，行为不变；内容审计新增独立的"审计观察名单"`observe_user_ids`，名单内用户照审、不拦、命中照推 |
| D3 | 上线节奏 | 观察名单先填 16、2、22，观察 3 天后清空再开拦；由运营负责提前通知用户 16、22 |
| D4 | Jev 故障时 | 继续放行（fail-open），同时立刻推微信告警 |
| D5 | 推送渠道 | sub2api 内置 Server酱 Turbo 推送（运营开会员，每天 1000 条） |
| D6 | 推送内容 | 不带违规原文，只带用户邮箱、分组、模型、类别、分数、内容哈希、request_id、后台链接 |
| D7 | 命中合并 | 按用户 30 分钟窗口：窗口内第一次命中立即推送；之后的命中在窗口结束时合并成一条推送。哈希预检拦下的只计数，不单独推送。命中类推送每天最多 300 条，到上限时推一条"已达上限" |
| D8 | 系统告警 | 402 立即推送；所有 key 都被冻结时推送；5 分钟内审计失败率 >20%（至少 20 次调用）时推送；恢复时推一条"已恢复"。同一告警在恢复前最多每 30 分钟推一次。ops 告警只推 P0（critical） |
| D9 | 日报 | 每天北京时间 09:00 推送前一天的数据：审计次数、缓存命中、命中和拦截（观察名单单列）、命中最多的用户、Jev token 和估算费用、推送条数、告警次数 |
| D10 | 降本 | 打开违规哈希预检、模型固定为 `jev-1.14.0`（以上两项是生产配置）；结果缓存 24h；审计挪到选完账号、真正转发之前；token 记账；402 单独冻结并发出告警 |
| D11 | 缓存细节 | 只缓存调用成功的结果，存 13 个分数而不是结论；命中缓存的请求照样写日志，标 `cached`、耗时记 0；违规内容走已有的哈希预检；缓存 key 含引擎、模型和规则版本 |
| D13 | 审计后移（2026-11-15 Q16） | 本次不做。结果缓存已覆盖原样重试；上线一周后看日报数据，再决定是否只为 `/v1/messages` 单独出 change |
| D14 | 默认配置调到最优（2026-11-15） | 代码默认值：结果缓存 1440 分钟、违规哈希预检默认开启、TypeSafe 默认模型固定为 `jev-1.14.0`；推送默认值为每日上限 300、合并窗口 30 分钟、日报 09:00、ops P0 开启。生产已有配置由上线步骤显式改写 |
| D12 | 其他默认 | 观察名单放在风控中心的设置对话框里；掉线监控脚本不动、共用同一个 SendKey；推送失败最多重试 1 次；OpenAI Responses 的 WebSocket 多轮审计位置不动 |

## 范围外（Non-goals）

- 模板剥离、问题精简、长文本截断策略、Noul 粗筛：需要影子验证，另出 change。
- 改变 OpenAI cyber_policy 的行为。
- 多实例下命中合并窗口的跨实例一致性：生产是单实例；每日上限计数和日报防重放在 Redis 里。
- 支持 Server酱 以外的推送渠道。

## 验收标准

1. 观察期内：用户 16、2、22 不会被拦截，命中能推到微信并标明"观察中"；其他用户正常拦截；日报按时送达。
2. 模拟 402：1 分钟内收到告警，恢复后收到"已恢复"；审计日志写的是真实错误 `typesafe API status 402`。
3. 日审计调用量比当前约 10 万次至少降低 50%（预计降 60–75%），以 token 记账数据为准。
4. 推送中不出现违规原文和 SendKey；SendKey 不写进日志和接口返回值。

## 上线步骤

1. dev 开发完成后，打带完整更新说明的 annotated tag，由 release.yml 构建镜像。
2. us-40 先 `pg_dump -Fc` 备份，再升级（迁移 `248a` 会把现有风控白名单复制进 `observe_user_ids`，保持现有行为）；审计保持关闭。
3. 后台填 SendKey，发测试推送。
4. 运营给 TypeSafe 充值后：模型固定为 `jev-1.14.0`，打开违规哈希预检，确认观察名单为 16、2、22，打开审计。这一步需要用户再确认。
5. 观察 3 天。
6. 清空观察名单，正式开拦。这一步需要用户再确认。
